# TLS

## Generation

TLS assets are generated by the `certificate_authority` role on the first Vault node.

The role creates:

```text
/opt/vault/tls/tls.key
/opt/vault/tls/tls.csr
/opt/vault/tls/tls.crt
/opt/vault/tls/tls_ca.csr
/opt/vault/tls/tls_ca.pem
```

The private key is RSA 2048 in the delivered role.

## Subject Alternative Names

The generated CSR includes SAN entries for:

- loopback
- all three Vault node IPs
- the Keepalived VIP
- DNS forms of those addresses
- localhost
- all three node short names
- the cluster name
- `*.lab.local`

This allows the same TLS material to be used across the cluster in the lab topology.

## Distribution

The `vault_certificate_install` role currently uses Ansible `fetch` to copy:

```text
tls.key
tls.crt
tls_ca.pem
```

from node 1 to the Ansible controller and then `copy` to nodes 2 and 3.

The working repository originally used an `Ansible/buffer/` directory. For a public repository, generated private keys and certificates should not be committed.

## Vault listener

All node templates configure a TCP listener on ports 8200/8201 with TLS enabled and paths under `/opt/vault/tls`.

## Trust store

The Vault installation role copies `tls.crt` to the system CA trust anchors and runs `update-ca-trust`.

## Security considerations

This certificate design is appropriate as a self-contained lab demonstration. For production use, prefer a controlled PKI, node-specific server certificates, short-lived certificates/rotation, and private-key handling that does not stage keys on a general-purpose automation controller.
